Specification Card Demo

The Open Intelligent Store Specification (OISS) lets each store-intelligence source, from shelf-scanning robots and shelf cameras to people counting, loss-prevention vision and the retailer's own planogram, publish what it saw as standard records. Any consumer, from a store operations dashboard to an AI agent, then reads one record set for the whole store. OISS also includes a blueprint for using that data with agent platforms, so the value shows right away.

Key Value Propositions:

  • One View Across Vendors: on-shelf availability, traffic, front-end queues and loss-prevention exceptions line up on one store layout and one item master
  • Use Cases No Single Vendor Covers: replenish the out-of-stocks with the most shopper traffic first, and close a task only when the next shelf scan shows it fixed
  • No Lock-In: change or add vendors without rewiring every report, task tool or agent downstream
  • Agent-Ready: a query API and an MCP server let any agent platform read the data and write tasks back
  • Built on What Retailers Use: GTINs from the item master, the retailer's own store numbers, and CloudEvents, GS1 and ONVIF underneath

Architecture Diagram

Key Features

  • Store Operations Assistant: a reference orchestrator that routes each question to a specialized agent reading OISS through MCP
  • Multi-Agent System - Five specialized agents:
    • Availability Agent - Prioritizes replenishment by lost sales and closes a task only when the next shelf check shows it fixed
    • Price and Label Agent - Fixes wrong shelf prices through the electronic shelf label or a task
    • Front-End Agent - Opens a lane when a queue grows and feeds queue trends to labor scheduling
    • Loss Prevention Agent - Ties a front-end exception to an anonymous shopper path, a missing item and the evidence, for a person to review
    • Store Insights Agent - Measures display lift, compares stores and flags where two vendors disagree about the same shelf
  • Seven Record Types: StoreLayout, ShelfObservation, ZoneMetric, ShopperPath, Incident, Evidence and Task, versioned together as v0.1
  • Adapters and Validation: one adapter per vendor export, the oiss-validate schema validator, and a mapping from ShelfObservation to a GS1 EPCIS 2.0 ObjectEvent
  • Storage and Query: current state and history for every record, and an evidence store that enforces retention
  • Agent Access: an MCP server with tools such as out-of-stocks since a time, zone status, open incidents and create task
  • Access Control: each record's privacy class limits what a reader sees, and guardrails check agent actions before they reach a store system
  • Traceability: every record carries its source system, model and version, a confidence and links to evidence

Record Types

RecordWhat it says
StoreLayoutZones, fixtures, shelves and facings, with the planogram and camera placement
ShelfObservationOn-shelf availability, planogram compliance and price integrity at one facing
ZoneMetricTraffic, dwell, queue length, wait time and open lanes for one zone over one interval
ShopperPathAn anonymous shopper path on the floor plan; off by default
IncidentA loss-prevention exception or safety incident, with a confidence, for a person to review
EvidenceA clip or image reference with time range, camera, retention and access roles
TaskA store task, such as replenish or fix a shelf tag, and its status

What Adoption Takes

Data Requirements

  • A store layout with the planogram, keyed by GTIN and the retailer's own store number, plus shelf observations, is enough to start on on-shelf availability. Traffic, front-end and loss-prevention data can follow one feed at a time.

Deployment Options

  • No rip and replace: vendors keep their own systems, and one small adapter per feed maps its export to OISS
  • Vendors that emit OISS natively need no adapter
  • The demo runs entirely in a web browser on synthetic data

Software Used in This Blueprint

Open Standards

  • CloudEvents 1.0
  • GS1 EPCIS 2.0 and GS1 identifiers (GTIN, GLN)
  • ONVIF Profile M object classes
  • JSON Schema 2020-12
  • Model Context Protocol

Reference Implementation

  • TypeScript store simulator
  • React and SVG demo app
  • Python validator (oiss-validate)
  • An NVIDIA-hosted model for the Store Operations Assistant (coming in milestone M4)

Ethical Considerations

OISS carries no faces or biometrics. Records are aggregates by default, shopper paths are anonymous, with ids that rotate (every 15 minutes in the demo), and are off unless a retailer turns them on, and every record carries a privacy class, a retention date and access roles where it needs them. Incidents are for a person to review, never an automatic accusation. Retailers adopting OISS should check it against their own privacy, labor and loss-prevention policies and local law.

Please report issues and concerns on GitHub.
